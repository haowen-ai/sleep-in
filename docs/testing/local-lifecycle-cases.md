# Mac local installation and background lifecycle test design

Status: **test design, not execution evidence**. Feature implementation is paused pending review of the complete test plan. This matrix derives from PRD §§14.1–14.5 and acceptance A17–A23; an automated policy test does not establish actual macOS power, permission or packaging behavior.

## Scope and execution rules

- **P0:** blocks the local vertical slice: credentials, isolated startup, duplicate prevention, correct lifecycle and honest health. **P1:** blocks claims of a complete Mac release: clean-device packaging, native permissions, real power trials, persistence and update recovery. **P2:** optional functionality, required only when advertised/enabled.
- **U** = deterministic unit test with temporary state. **I** = isolated integration test using real app/store/worker/n8n and synthetic workflows, random reserved loopback ports. **M** = observed trial on an explicitly designated physical Mac. **B** = browser/UI automation against the isolated instance. Simulated power callbacks establish software policy only; they do not replace M.
- All examples use synthetic SQLite → Python → JavaScript input (three rows), a deterministic report and a run-unique event ledger. A separate long-running synthetic workflow provides a controllable midpoint and cancellation acknowledgement. No real database writes, external messages, QMT, credentials or business integrations.
- Automated tests must never register login/background items, modify global power settings, lock/sleep/reboot/log out the user's Mac, toggle VPN/network, unplug power, drain its battery, or acquire a long-lived sleep assertion as an incidental test. Where needed, inject only the OS boundary and test actual persisted state and process lifecycle.
- Each M trial needs the operator's explicit authorization for the named device actions and a recovery plan. VM results may establish UI/installation behavior but cannot establish MacBook battery/lid behavior. Do not request Accessibility or Full Disk Access to make this suite pass.
- Run on macOS 13+ Apple silicon first, recording the exact OS build/hardware. Intel, additional OS versions, signed/notarized distribution and optional runtimes each need separate evidence before support is advertised.

## Common fixtures and evidence

**F0 — pristine:** new private application state, no records except store metadata, no previous app/runtime installation in the test account. For clean-install claims the Mac must have no independently installed Python, Node, Docker or Xcode Command Line Tools. Existing developer machines cannot establish F0 clean-device packaging.

**F1 — ready:** isolated installed application with fresh local administrator, pinned runtime manifests, real n8n orchestration and the synthetic three-node workflow published. The web listener is on loopback. Notifications are off.

**F2 — existing:** separate fixtures for current admin/operator users, disabled users, v1 samples/tasks, migrated records and restored backups. Keep a pre-test snapshot of password hashes, user IDs, permissions, source/version IDs and session IDs. Do not print hashes or session tokens in shared evidence.

**F3 — schedule:** unique workflow/occurrence keys, 1-minute synthetic intervals for short integration trials, a next-due occurrence at least 2 minutes ahead for physical trials, and a long-running synthetic run with a recorded midpoint. Do not reduce the clock interval to claim real daily continuity.

Each executed case records: case ID; UTC and local start/end; tester; artifact/build hash; OS/architecture; clean/existing profile; runtime/n8n versions; setup; actual result; pass/fail/blocked; linked evidence; deviations; cleanup. A blank or planned row is **not run**, not passed. Shared evidence excludes credentials, secrets, cookies and private endpoints.

Evidence abbreviations:

- **UI:** screen recording or screenshots plus accessible text at relevant transitions; redact private data.
- **DB:** before/after synthetic run, occurrence, version and node records; count logical step invocations and artifact checksums.
- **PROC:** supervisor/app/worker/n8n PIDs, parent relationships, start times and lock ownership; identify CLI n8n per-run versus persistent-service architecture accurately.
- **HEALTH:** timestamped component readiness, errors and recovery events; no green aggregate when a required component is unready.
- **POWER:** read-only `pmset -g assertions`, `pmset -g batt`, and relevant `pmset -g log` excerpts before/during/after; assertion-owner PID and system sleep/wake events; display-lock evidence separately. Do not infer system wakefulness from a lock screenshot or a UI status label. Capture at transition points and periodically during soak; record any observation gaps.
- **PREF:** persisted run preference, background registration status and stop/recovery reasons, with no secret values.
- **NET:** actual bound sockets, HTTP statuses and response payload inspection from loopback/non-loopback request fixtures.

## Physical power, locking and continuity

These M trials are **not performed by this design task**. Obtain explicit approval for unplug/replug, locking/display-off, native permission changes, explicit sleep, lid closure, logout or reboot before each named trial. Never deliberately exhaust the battery, induce overheating, change global power settings or disable FileVault. Low/critical-power behavior can first use simulated OS events; dangerous device states are not a release test shortcut.

## Test implementation sequence and decision gates

1. Review expected lifecycle states before writing more feature code: `installing → permission_pending / starting → running → degraded / draining → stopped`; workflow pause is an independent admission setting; power assertion and OS registration have independent real statuses. Resolve disagreement between UI labels, stored preference and actual process ownership before implementation.
2. Implement U cases first using temporary Store and a fake OS-boundary adapter; tests must inspect real persisted account/lifecycle state rather than merely matching mocked function calls. Add I subprocess tests with real port conflicts, concurrent launches, crashes, n8n execution, drains and occurrence ledgers. Do not count expected missing-module failures as passed tests.
3. Run B checks for both English and Simplified Chinese, especially permission pending, default login, draining/cancelling, stopped and missed-occurrence states. Screen closure and browser closure must be tested distinctly from explicit Quit.
4. Before M, create an operator-approved trial sheet with device, OS/build, required actions, safe battery reserve, planned duration, rollback/cleanup and where evidence is stored. Confirm a second access/recovery path for crash/reboot trials. Never execute physical state changes just because this matrix lists them.
5. P0 U/I/B failures block local vertical-slice acceptance. P1 clean Mac, SMAppService, signature and POWER cases remain **blocked/not run** until actual artifacts/devices/consent exist; code review, mocks, existing-machine launch and short interval tests cannot close those gates. P2 catch-up can be explicitly out of scope and omitted from UI.

## Current evidence at implementation pause

- `tests/test_local_accounts.py`: eight automated cases passed on an isolated temporary Store before the pause: explicit local/loopback initialization guard; initial credentials and changed-hash hint; existing user/script/version/workflow/task/connection preservation. This is partial evidence for AU-01/AU-02/AU-04/AU-05, not full UI/session/security acceptance.
- `taskconsole/local_accounts.py`: initial implementation exists; `initialize_local_account(store)` must run before sample seeding. Root integration handles route/network/session boundaries. Its readiness must be reassessed against this full matrix, including existing empty-install and restored-metadata edge cases.
- `tests/test_local_service.py`: five tests were written first and currently fail because `taskconsole.local` does not exist. They cover intended single-instance lock, persistent explicit-stop preference, stale status, local child environment and explicit registration consent. These are **red tests, not implemented service behavior**.
- No launcher, native SMAppService helper, supervisor or packaging script was implemented by this subsystem before pause. No login item registration, global power change, physical power trial or real sleep assertion was performed. No clean-Mac, signing, battery, overnight or restart claim has been established.
